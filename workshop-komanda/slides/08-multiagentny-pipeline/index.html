Кирпич · один агент
С чего начинается каждый агент — ТЗ
Роль — кто одной фразой
Задачи — 3–5 операций глаголами (вход → выход)
Инструменты — что вызывает: поиск, расчёт, документ
Память — что знает про компанию + история
Правила — 3–5 «если X — то Y», включая «никогда»
Интеграции — откуда вход, куда выход и кому
Безопасность — где зовёт человека
Критерий готовности — 3–5 реальных кейсов
Это один сотрудник на одну задачу. Но фичу, миграцию, разбор большого кода один агент не вытянет — там нужен конвейер.
Пайплайн — это несколько таких ТЗ, передающих работу друг другу
Когда задача больше одного агента
Почему «спланируй и сделай» в одном промпте ломается

План прозой теряет критичное

Консилиум ролей планирует текстом, имплементер читает текст — и выпадает интеграция, токен, существующий модуль: никто не написал явно, значит для следующего агента этого не существует.
1Forced schema — план не проза, а форма с обязательными слотами. Пустой слот = план невалиден, забыть секцию нельзя
2Independent gate — план проверяет отдельный агент в чистом контексте. Он не планировал, читает только файлы и ищет дырки
3Context injection — имплементеру даём не «весь контекст», а его срез: спека модуля + ровно нужные токены, доки, ссылки на код
Artifacts first: решение, которого нет в файле, — не существует
Конвейер с проверками
Как это работает на примере моей dev-team
1Scout — разведка ДО плана: какие токены, доки, код, интеграции. Решение не проектирует. → recon
2Architect — заполняет план-форму. Каждый модуль ссылается на пункты разведки. → plan
🚦Gate-A — НОВЫЙ агент, чистый контекст. Полнота / покрытие разведки / инъекция ресурсов. PASS → дальше · FAIL → план на v2
4Spawn — на каждый модуль свой бриф: спека + срез разведки + критерий. Запускаются по командам, не сами
🚦Gate-B — для UI: литеральные проверки спеки (иконки, цвета) через grep/jq, а не «на глаз»
Гейт — отдельный незаинтересованный агент. 2 FAIL подряд → стоп: задача сформулирована нечётко
